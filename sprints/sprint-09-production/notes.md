# Design Notes

This sprint is minimal on design — it is mostly infrastructure and verification work, not new UI.

- Any user-visible surface introduced this sprint (e.g. a cookie/analytics notice, if the team decides one is warranted) should follow DESIGN_SYSTEM.md's existing patterns rather than introducing a new visual language.

# Technical Notes

## Libraries

| Library | Purpose | New for this sprint? |
|---------|---------|----------------------|
| Sentry SDK | Error logging and monitoring in production, per ARCHITECTURE.md "Monitoring" and DEPLOYMENT.md "Observability" | Yes |
| Vercel Analytics / Google Analytics | Traffic and usage analytics, per DEPLOYMENT.md "Required Environment Variables" (`GOOGLE_ANALYTICS_ID`, previously marked "(Future)") | Yes |

Both libraries activate environment variables DEPLOYMENT.md previously marked "(Future)": `SENTRY_DSN` and `GOOGLE_ANALYTICS_ID`. This sprint is the first time either is wired up.

## Patterns

- **Environment-variable-driven configuration**: all monitoring/analytics keys and IDs are read from environment variables (`.env.local` for development, Vercel Environment Variables for hosted environments), following `.env.example` conventions and `.ai/SECURITY.md`'s "Secret Management" and "Environment Variables" sections. Never hardcode a DSN, tracking ID, or any other key directly in source.
- **Preview before Production**: security header changes are validated in a Preview deployment before being enabled in Production, consistent with DEPLOYMENT.md's environment strategy (Development → Preview → Production).
- **Repository-driven sitemap generation**: `sitemap.xml` is generated by reading from the same repository layer (`BusinessRepository`, `CategoryRepository`, etc.) that pages already use — never a separately maintained, hardcoded URL list, per ARCHITECTURE.md's "Never hardcode business data."
- **Verify, don't assume**: "wired up" and "verified receiving real events" are treated as two distinct, separately checked states throughout this sprint (see README.md Risks) — configuration succeeding is not proof the integration works end-to-end in production.

## Risks / Assumptions

- **The Robots.txt/Sitemap/Metadata split with Sprint 7 is deliberate and must not be re-litigated.** Sprint 7 (Quality) already audited and fixed **per-page** SEO — titles, descriptions, Open Graph tags, structured data, headings — across all existing routes. This sprint builds the **site-wide crawl infrastructure** that has never existed before (`sitemap.xml` generation across all business/category/community routes, `robots.txt`) and performs one **final** pre-launch sanity check of metadata, not a fresh audit. Treat any metadata finding in this sprint as a possible regression since Sprint 7, not as new discovery work.
- **The About/Contact/Privacy/Terms gap is real and unresolved.** `.ai/ROADMAP.md`'s "Phase 5: Community Pages" (About, Community, Contact, Privacy, Terms, 404) and `.ai/TESTING.md`'s "Critical User Journeys" (which explicitly lists "Contact page") were never assigned to any of this project's actual 10 sprints — Sprint 5 became Search and Sprint 6 became Community Content instead of what ROADMAP originally called "Community Pages." As a result, there is currently no scheduled About page, Contact page, Privacy Policy, or Terms of Service page anywhere in this 10-sprint plan. Sprint 7 does cover a custom 404/error page, so 404 is not part of this gap. This sprint does not silently resolve the gap by adding these pages, and does not silently ignore it either — it is flagged here, in README.md's Risks, and in retrospective.md's AI Memory Update as something the project owner must decide before launch sign-off: (a) add a minimal About/Contact/Privacy/Terms page as a late addition to this sprint, or (b) explicitly accept the gap for a v1 launch with no user accounts/data collection and revisit before any feature that collects user data ships.
- Assumes Sentry's free/starter tier is sufficient for this project's current scale — revisit if event volume or team size grows.
- Assumes Vercel Analytics and/or Google Analytics collection is compatible with `.ai/SECURITY.md`'s "Privacy" principles (data minimisation, purpose limitation, transparent data handling) — no personally identifying data should be sent to analytics beyond what these tools collect by default; revisit if custom event tracking is added later.
- Assumes security headers can be configured at the Next.js/Vercel platform level without requiring application code changes to existing pages — if any existing script or embed depends on a relaxed CSP, that dependency should be fixed rather than the CSP weakened, per SECURITY.md's "Content Security Policy" guidance to avoid `unsafe-inline`/`unsafe-eval` "unless there is a documented exception."
